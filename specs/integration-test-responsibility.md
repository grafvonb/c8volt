# Integration Test Responsibility Boundary

This repository keeps integration-test runtime evidence separate from planning and backlog artifacts.

## Runtime Test Responsibilities

Integration tests may prove and record observable execution facts:

- selected default-local profile and observed Camunda version
- command arguments, stdin, stdout, stderr, exit code, and duration
- suite-owned resource keys used for assertions
- before-state and after-state for completed mutations
- dry-run, submitted, no-wait, retained, cleanup-failed, skipped, unsupported, or failed outcomes
- failure class and skip reason when runtime proof cannot continue

Integration tests must not create product backlog proposals, embedded BPMN proposals, or command-extension proposal reports as part of normal execution.

## Missing Prerequisites

When a scenario cannot create or discover the required state through current c8volt commands and available embedded BPMN fixtures, the test should do one of the following:

- skip with a precise prerequisite-missing reason when the scenario cannot make a meaningful runtime assertion
- record a partial or dry-run outcome when that is the behavior under test
- fail when a required prerequisite was supposed to be available for the current feature slice

The missing command capability, embedded BPMN fixture, or setup path belongs in a spec-owned gap artifact such as `specs/<feature>/gaps.md`.

## Controlled Dirty-State Setup

Some high-value c8volt behavior exists specifically because c8volt avoids or repairs unsafe Camunda states. Integration tests may therefore create deliberately inconsistent state through direct Camunda APIs when all of the following are true:

- c8volt commands intentionally prevent creating that state in normal use
- the inconsistent state is required to prove cleanup, cascade, warning, repair, or reporting behavior
- setup remains scoped to disposable integration targets and recorded suite-owned keys
- the test records the setup path as runtime evidence without generating backlog proposal files
- the matching spec gap explains whether the missing setup is a test-only corruption helper, a reusable embedded BPMN fixture need, or a product command/setup capability

For example, orphan-child cleanup should be proven by creating a normal call-activity family through c8volt, then using Camunda APIs directly to delete a parent process instance without c8volt's cascade-safe deletion. That setup is not a proposal for a c8volt command that creates orphans; it is a controlled test-only corruption path used to prove c8volt can discover and repair the mess.

## Spec-Owned Gap Tracking

Gap artifacts may describe:

- required state or process behavior
- affected commands and flags
- affected Camunda minor versions
- blocked runtime proof
- intended operator value
- current runtime-test behavior until the gap is closed

These artifacts are maintained by planning or implementation work, not generated by integration tests.

## Deprecated Pattern

Earlier 255 and 256 integration artifacts used `proposals-command.json` and `proposals-embedded-bpmn.json` as runtime evidence files. Do not extend that pattern. New or corrected integration work should use runtime outcomes and spec-owned gap artifacts instead.
